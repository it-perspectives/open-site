# OpenSite

Открытый контракт сайта для отдела тестирования и разработчиков. Описывает
страницы, параметры URL и компоненты интерфейса, к которым обращаются тесты.
Формат не зависит от языка программирования и frontend-фреймворка; контракт
можно записать в YAML или JSON.

Статус: начальная версия спецификации **0.1.0**, черновик. Предполагаемое имя
npm-пакета — `@it-perspectives/opensite`. Публикация пакета и релиза пока не выполнена.

- В документе обязателен непустой набор `pages`.
- У страницы обязательны `title` и `path`. Карты `searchParams`, `pathParams`
  и `components` необязательны.
- У каждого inline-компонента обязательны `description`, `role` и `locator`.
  Общие определения переиспользуются через локальный `$ref`.
- `role` выбирается из фиксированного словаря ARIA-ролей спецификации.
- `locator` задаёт способ поиска: `role`, `testId`, `label`, `placeholder`,
  `text`, `altText`, `title` или `css`.
- Компоненты могут содержать вложенные `components`; тест обращается к ним по
  идентификатору вида `filters.inStock`. Поиск выполняется внутри родителя.

```yaml
opensite: "0.1.0"
info:
  title: Каталог магазина
  version: "1.0.0"
pages:
  catalog:
    title: Каталог
    path: /catalog
    searchParams:
      q:
        description: Поисковый запрос.
        type: string
      page:
        description: Номер страницы с единицы.
        type: integer
        default: 1
        minimum: 1
    components:
      search:
        description: Поле поиска товаров.
        role: searchbox
        locator: { by: role, name: Поиск товаров }
      submit:
        description: Кнопка поиска.
        role: button
        locator: { by: testId, value: catalog-submit }
```

`role` описывает ожидаемую роль DOM-элемента. `locator` — декларативное описание
его адреса. Формат независим от тестовых фреймворков и библиотек автоматизации:
потребитель сам реализует поиск и проверку роли. По умолчанию текстовые локаторы
задают точное совпадение (`exact: true`). Контракт задаёт ожидаемое поведение
и временные границы проверок; выполняет проверки выбранный потребителем инструмент.

В нотации также доступны:

- `expect`: наличие, видимость, количество, текст, accessible name и состояния контролов.
- `states`, `defaultState`: состояния страницы и ожидания для каждого из них.
- `variants`: локали, размеры экрана, функциональные флаги и переопределения ожиданий.
- `access`: необходимость авторизации, роли пользователя и результат отказа.
- `forms`: поля, ограничения, ошибки, момент валидации и позитивные/негативные случаи.
- `transitions`: событие, предусловия и ожидаемый результат, включая переходы и уведомления.
- `invalidURLs`: неверные входные URL и ожидаемые ошибки, редиректы или нормализация.
- `definitions.components`: общие компоненты; неизвестные и циклические ссылки запрещены.
- `meta`: теги, критичность, владелец, требования.
- `snackbars`, `snackbarPolicy`: снеки, сообщения, действия, закрытие, время жизни,
  сроки появления/исчезновения и правила очереди.

Для снеков есть [отдельное описание и план проверок](docs/snackbars.md).
Полный YAML/JSON-пример содержит страницу `account`: форму профиля, состояния,
контроль доступа, локализацию, успешный снек с Undo и ошибку с Retry.

API `resolvePage` возвращает описание страницы для состояния и варианта,
`getComponent` — данные компонента с учётом переопределений, `checkFormValues` —
проверку типизированных значений формы. Эти функции не запускают браузер.

```sh
npm ci --ignore-scripts
npm run verify
node bin/opensite.js lint examples/opensite.yaml --warnings-as-errors
node bin/opensite.js check-search examples/opensite.yaml --page catalog --search 'q=coffee&page=2'
```

Валидатор проверяет типы, обязательность, ограничения, значения по умолчанию,
примеры и соответствие параметров шаблонам маршрутов. Query-параметры бывают
`string`, `integer`, `number`, `boolean` и `array`; массив строк передаётся
повторением ключа: `tag=coffee&tag=sale`. Неизвестные параметры и повторение
скалярного параметра считаются ошибками. Адрес стенда передаётся тестом отдельно.

Контракт нужен для согласования интерфейса и устойчивых адресов компонентов.
Подготовку данных, авторизацию, выполнение действий и наблюдение результата задают тесты.
Успешная валидация файла сама по себе не доказывает соответствие сайта контракту.
